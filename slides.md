# Git Flow

Больше веток богу веток

<!-- TODO: Добавить иллюстрацию Git Flow -->

<!-- 
Этот рабочий процесс больше нравится командам, работающим с фиксированными релизами. Он позволяет четко определять границы и наполнение релиза, и поддерживать несколько одновременно существующих релизов чуть более явно.

Существуют две основные ветки - main и develop. Разработка проходит в фича-ветках, порождаемых от develop. По завершении разработки фичи код мержится в develop. 

Когда начинается подготовка релиза, от последнего коммита в develop формируется новая ветка - release. В нее допускается мержить исключительно багфиксы.

Когда релиз готов - он вливается в main. Каждый коммит в main - новый релиз.

Любые хотфиксы должны делаться в отдельной ветке, формируемой от main.

В настоящее время этот подход в чистую используется редко, в основном потому что он громоздкий. Но мне кажется важным вас с ним познакомить, потому что игры могут разрабатываться большими циклами с фиксированными релизами.

Главное помните: рабочий процесс - это не догма, которой вы обязаны следовать досканально. Это пример того, как работают другие команды. Адаптируйте его под себя, анализируйте что идет не так и не попадайте в карго-культ.
-->

# Merge-конфликты

Возникают, когда не понятно как применить изменения к файлу из разных источников

Конфликты - это очень распространенная штука в нашей работе. Не стоит их бояться, вы всегда можете вернуться к состоянию до конфликта и попробовать снова.

Разрешить конфликт - дать точный ответ как должен выглядеть файл после применения обоих изменений.

# Конфликты в Unity

Чаще всего возникают в файлах префабов, сцен и ассетах.

В бинарных файлах разрешить конфликт для git невозможно, он не знает как устроен файл. Не допускайте конфликтов в ассетах.

Файлы префабов и сцен - текстовые файлы со сложной структурой. С ними можно справиться с помощью `UnityYAMLMerge`.

# Управление историей

Помните, что история в git неизменяемая? Так вот, это не так.

Git защищает тебя, пока ты сохраняешь историю неизменяемой. Хочешь ее исправить? Берешь ответственность на себя.

Команды для исправления истории:

```sh{hide|1-2|4-5|7-8}
# Изменить последний коммит в ветке
git commit --amend

# Вернуть репозиторий в указанное состояние
git reset [--hard | --soft | --mixed] <commit>

# Добавить коммит, отменяющий изменения из указанного коммита
git revert <commit>...
```

# Merge и Rebase

Двигаем историю вперед, держа репозиторий в порядке (и не привлекая внимания санитаров)

Используем `git merge`, чтобы продвинуть вперед основную ветку.

Используем `git rebase`, чтобы подготовить изменения к слиянию.

`git rebase` безопасно использовать в своей ветке. Если все пошло катастрофически плохо - есть `git reflog`.

# git-lfs и совместная работа

А как внести правки в ссылку?

Для совместной работы с файлами в LFS используют блокирование файлов. Заблокированный файл может изменить только тот, кто его заблокировал. 

Этот процесс централизованный и реализован на сервере, управляющем LFS.

# .gitignore

Список файлов, на которые нужно забить

Чаще всего достаточно взять [стандартный](https://github.com/github/gitignore/blob/main/Unity.gitignore), может быть дополнить его под свою специфику.

Если какие-то файлы не влияют на работу с вашим проектом и, если их выкинуть, ничего не изменится - добавляйте в `.gitignore`.

Добавить в игнор - не значит выкинуть из истории.

# Смена контекста

Или что делать, если в пылу разработки новой фичи нужно показать текущую стабильную версию

Переключение контекста всегда отвлекает. Упростите себе задачу через привычки.

`git stash` прячет незакоммиченные изменения, оставляя рабочую область чистой.

```sh{hide|all}
git stash push --include-untracked
# ... поработали на другой ветке
# ... вернулись туда, где создали stash
git stash pop
```
